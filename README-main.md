# Orbit

An automated security tool built for teams too small to have a security
team. It scans a codebase, generates real tests that prove a
vulnerability is exploitable, fixes it, and verifies the fix doesn't
break anything else — before a human ever has to review it.

## Why

Most startups ship real products with no dedicated security review. The
vulnerabilities that hit them aren't exotic — they're the same
well-documented mistakes year after year (SQL injection, hardcoded
secrets, broken access control). The barrier isn't sophistication, it's
that nobody on a small team has the time, background, or budget to catch
them. Orbit automates that loop: detect, prove it's real, fix it, verify
the fix holds.

## How the backend works

The pipeline runs in four stages, and the key design decision underneath
all of them is: **use a deterministic, rule-based approach wherever one
is reliable, and reserve the language model for exactly the cases that
actually need judgment.**

**1. Detection.** [Semgrep](https://semgrep.dev), a static analysis
engine, checks the codebase against a small, focused set of detection
rules — one per attack category. This step involves no model call at
all: for well-known vulnerability classes, a deterministic scanner has no
false-positive risk from hallucination and is faster than an LLM
re-deriving the same pattern from scratch.

**2. Test generation.** For every finding, two tests are generated
automatically from a template specific to that vulnerability class:
- A **security test** that fires a real, canonical attack payload at the
  actual flagged function and asserts the exploit fails.
- A **functional test**, built from real data pulled from the target
  application's own database, that confirms legitimate use still works —
  this is what catches a fix that "solves" the vulnerability by breaking
  the feature.

Both tests are built against the function's real signature, discovered
by parsing the actual code, and the real table and column the function
queries, inferred from its actual SQL — not hardcoded to one shape.

**3. Fixing.** For a vulnerability class where the correct fix is a
known, mechanical pattern (parameterizing a query, moving a secret to an
environment variable), the fix is generated by a deterministic AST-based
rewriter — not a language model. This is a deliberate choice: for these
categories, a rule-based rewrite is more reliable than an LLM's
best-effort attempt, which research shows can correctly identify the
right *concept* while still getting the implementation subtly wrong. When
no deterministic pattern applies, the system falls back to a direct call
to Claude, scoped narrowly to that one file and that one fix.

**4. Verification and search.** A fix is never accepted on the strength
of its own tests alone. The system builds a real dependency graph from
the codebase's actual imports, finds the files connected to the one being
changed, and re-runs their existing tests against a captured baseline —
so a file that was already failing for unrelated reasons is never
mistaken for a new regression. If a fix passes its own tests but breaks a
connected file, it's reverted on disk and a different candidate is tried.
Only a fix that clears both checks is presented as resolved.

## What's tested and proven today

The full pipeline above is built and verified end to end for two
categories: **SQL injection** and **hardcoded secrets**. Both have a
working detector, a working test generator, a working deterministic
fixer, and a passing regression suite (`backend/dev_tests/`) that
includes deliberate edge cases — a pattern the fixer can't handle,
correctly declined rather than mishandled; a dependent file with an
already-failing test, correctly not mistaken for a new regression; and a
synthetic scenario proving the backtrack path genuinely reverts a file
and tries an alternate approach.

The other attack categories shown in the frontend demo (XSS, SSRF,
broken access control, insecure deserialization, and others) represent
the intended scope of the product; the same detect-test-fix-verify
mechanism is designed to extend to each of them, following the same
process used for the first two — checking whether the correct fix is a
mechanical pattern or genuinely needs a model, before writing any fix
logic.

## Running the backend

```bash
cd backend
pip install semgrep pytest
python app/init_db.py
python pipeline.py            # runs the full pipeline end to end
pytest dev_tests/ -v          # runs the regression suite
```

## How the frontend and backend fit together

The frontend is a self-contained, interactive demo of what the finished
product looks and feels like — the graph visualization, the fix search,
the verification flow — built to communicate the product experience
directly, independent of any server. The backend is the real mechanism
that experience is modeled on, running against actual code.

Connecting them into one live system is a matter of exposing the backend
as an API — wrapping `pipeline.py`'s stages as endpoints (scan, generate
tests, fix, verify) — and pointing the frontend's existing UI at that API
instead of its local demo data, with the visualization driven by the
pipeline's real, structured output (the same finding, candidate, and
verification data the backend already produces) rather than scripted
values. Because the backend already returns exactly that shape of data,
the integration work is in the API layer and the network-handling code,
not in redesigning either side.
